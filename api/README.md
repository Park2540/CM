# สัญญา API (Contract-first)

`openapi.yaml` คือข้อตกลงกลางระหว่างหน้าบ้านและหลังบ้าน แก้ไฟล์นี้ก่อนเสมอ แล้วจึงแก้โค้ด

เปิดอ่านเป็นเอกสาร: วางไฟล์ใน https://editor.swagger.io หรือใช้ส่วนขยาย OpenAPI ใน VS Code

## ขั้นตอนเมื่อเพิ่มหรือแก้ endpoint

1. แก้ `api/openapi.yaml`
2. `npm run api:types` เพื่อสร้าง `src/app/api/schema.ts` ใหม่ (ห้ามแก้ไฟล์นั้นด้วยมือ)
3. `ng build` แล้วแก้จุดที่ type ไม่ตรง
4. แก้หลังบ้าน: ตรรกะใน `backend/src/domain/` และ route ใน `backend/src/routes/` (ดู [backend/README.md](../backend/README.md))
5. ฝั่งหน้าบ้านเรียกผ่าน service ใน `src/app/pages/service/` ด้วย `HttpClient` + `apiUrl()`

## เชื่อมต่อหลังบ้าน

แก้ `src/environments/environment.ts`:

- `apiBaseUrl`: ที่อยู่ของหลังบ้าน (`backend/`) ตอนพัฒนา `npm start` ส่งต่อ `/api` ไปที่ http://localhost:3000

## สถานะการย้ายไปใช้ API

## โครงสร้างโค้ด

- `src/app/pages/service/` — service ฝั่งหน้าบ้าน: เรียก API และแปลงข้อมูลให้หน้าจอ (ไม่มีข้อมูลตัวอย่าง)
- `backend/src/routes/` — endpoint ของหลังบ้าน (รับคำขอ ตรวจสิทธิ์ ตรวจข้อมูล)
- `backend/src/domain/` — กฎทางธุรกิจ ข้อมูลตั้งต้น และตัวสร้างแผนงาน/ไทม์ไลน์/งวดงาน
- `backend/src/db/` — เก็บข้อมูลลง MongoDB

## ข้อตกลงสำคัญสำหรับหลังบ้าน

- error ตอบเป็น `application/problem+json` และ `title` เป็นข้อความภาษาไทยที่แสดงผู้ใช้ได้ทันที
- หลังบ้านเป็นผู้คำนวณระดับผู้อนุมัติ (`approvalLevel`) กำไร-ขาดทุน ไทม์ไลน์ และสถานะงวด
- หลังบ้านบันทึก Audit Log ทุกครั้งที่ข้อมูลเปลี่ยน หน้าบ้านไม่มี API เขียน Audit Log
- ตัดสินคำขอที่ไม่ใช่ `pending` ต้องตอบ `409` ส่วนไม่อนุมัติโดยไม่มีเหตุผลต้องตอบ `422`
- `/auth/me` ส่ง `permissions` ของผู้ใช้มาให้หน้าบ้านใช้ซ่อน/แสดงปุ่ม แต่หลังบ้านต้องตรวจสิทธิ์ซ้ำทุกคำขอ
- ข้อมูลอ่อนไหวของบุคลากร (`sensitive`, `paidAmount`) ส่งเฉพาะผู้มีสิทธิ์ `personnel.sensitive` และละเว้นค่าที่ผู้ไม่มีสิทธิ์ส่งมา
- รหัสบุคลากรและประวัติการแก้ไข หลังบ้านเป็นผู้สร้าง
- โครงการมี 3 ขั้นก่อนเริ่มก่อสร้าง: เปิดโครงการ (สถานะ `pending-contract` ยังไม่มีมูลค่า/วันที่) → บันทึกสัญญา → ตั้งค่างานก่อสร้าง (สร้างไทม์ไลน์และงวดงาน) ข้อมูลรายโครงการตอบ `409` จนกว่าจะครบทั้งสองขั้น ส่วน Dashboard การเงินนับมูลค่าตั้งแต่บันทึกสัญญา
- กลุ่มโครงการ (`ProjectGroup`, ใช้กับ `GET /projects?group=`): ในมือ = รอทำสัญญา + กำลังดำเนินการ, เสร็จแล้ว = ส่งมอบแล้ว (`handedOverAt`), อยู่ในประกัน = ส่งมอบแล้วและ `warrantyUntil` ยังไม่ถึง หลังบ้านเป็นผู้คำนวณวันหมดประกัน
- งานย่อยรายโครงการ (ขั้นที่ 2 ของหน้าตั้งค่า): `excludedTasks` = รหัสงานจากแม่แบบที่ไม่ทำ (ตัดจุดตรวจ/หมุดหมายไม่ได้ ตอบ 422), `customTasks` = งานที่เพิ่มเอง หลังบ้านออกรหัส `<ขั้นตอน>.X<ลำดับ>` และวางต่อจาก `afterCode` ส่วน preview ต้องส่งงานที่ตัดออกมาด้วย (`included: false`) ให้ผู้ใช้เลือกกลับได้
- ทีมงานโครงการ: ผู้จัดการโครงการคนแรกคือ `responsibleName` ของโครงการ (ต้องมีอย่างน้อย 1 คน), `/team` สร้างจากผู้รับผิดชอบที่มอบหมาย; ผู้รับเหมาช่วงมอบหมายตามขั้นตอนในไทม์ไลน์ หลังบ้านคำนวณความคืบหน้า/สถานะจากขั้นตอนนั้น ยกเลิกไม่ได้เมื่อเริ่มงานแล้ว (409) และส่ง `contractValue` เฉพาะผู้มีสิทธิ์ `project.manage`
- ตั้งค่างานก่อสร้าง: หลังบ้านเป็นผู้กำหนดตัวเลือก (`/settings/construction-options`) และงานที่แต่ละตัวเลือกเพิ่ม/เปลี่ยน (อยู่ที่ `when` ใน `backend/src/domain/construction-plan.template.ts`) หน้าบ้านสร้างฟอร์มจากรายการนั้นเอง แก้การตั้งค่าไม่ได้ (`409`) เมื่อเริ่มรายงานความคืบหน้าแล้ว
- บัญชีผู้ใช้ (`/user-accounts`, ต้องมีสิทธิ์ `user.manage`): 1 บุคลากร 1 บัญชี (ซ้ำ 409), อีเมลซ้ำกับบัญชีอื่นไม่ได้ (422), บทบาทกลุ่ม `external` สร้างจากทะเบียนบุคลากรไม่ได้, บทบาทกลุ่ม `project` ต้องมีอย่างน้อย 1 โครงการ ส่วนกลุ่ม `internal` เก็บ `projectCodes` ว่าง (= ทุกโครงการ)
    - สิทธิ์ที่ใช้จริง = `permissions` ของบทบาทใน `/roles` + `grantedPermissions` − `revokedPermissions` หลังบ้านต้องใช้ค่านี้ตอบ `/auth/me` และตรวจสิทธิ์ทุกคำขอ
    - กันการล็อกตัวเองออก: แก้บทบาท ถอน `user.manage` หรือระงับบัญชีของตัวเองไม่ได้ และต้องมีเจ้าของบริษัทที่ใช้งานได้อย่างน้อย 1 บัญชี (409) มอบบทบาท `owner` ได้เฉพาะเจ้าของบริษัท
    - สร้างบัญชีแล้วสถานะเป็น `invited` และส่งลิงก์ตั้งรหัสผ่านทางอีเมล ระงับแล้วต้องตัด session ทุกอุปกรณ์ทันที
- สมัครสมาชิก (`POST /auth/register`, ไม่ต้องล็อกอิน): ได้คำขอสถานะ `pending` และเข้าสู่ระบบไม่ได้จนกว่าจะอนุมัติ อีเมลที่มีบัญชีหรือมีคำขอรออนุมัติอยู่แล้วตอบ 409 เก็บรหัสผ่านแบบ hash เท่านั้น
    - อนุมัติ/ปฏิเสธได้เฉพาะผู้ใช้ที่มีบทบาท `admin` หรือ `owner` (ตรวจจากบทบาท ไม่ใช่สิทธิ์รายคน) คนอื่นที่มี `user.manage` ดูรายการคำขอได้แต่ตัดสินไม่ได้ (403)
    - อนุมัติ = ผูกกับบุคลากรในทะเบียนที่ยังไม่มีบัญชี + กำหนดบทบาท/โครงการ/สิทธิ์ตามกฎเดียวกับ `POST /user-accounts` แล้วสร้างบัญชีสถานะ `active` ทันที (ผู้สมัครตั้งรหัสผ่านไว้แล้ว) ส่วนปฏิเสธต้องมีเหตุผล (422) และคำขอที่ตัดสินแล้วตอบ 409
    - หลังบ้านช่วยจับคู่ `suggestedPersonnelId` จากรหัสบุคลากร อีเมล หรือชื่อ (เฉพาะบุคลากรที่ยังไม่มีบัญชี)
- เข้าสู่ระบบ (`POST /auth/login`): คืน `accessToken` (Bearer) + `expiresAt` (8 ชั่วโมง หรือ 30 วันเมื่อ `remember`) + `user` ทุก endpoint อื่นนอกจาก `/auth/login`, `/auth/register` ต้องมี token ไม่มี/หมดอายุ/บัญชีถูกระงับระหว่างใช้งาน ตอบ 401 แล้วหน้าบ้านพากลับหน้าเข้าสู่ระบบ
    - อีเมลหรือรหัสผ่านผิดตอบ 401 ข้อความเดียวกัน (ไม่บอกว่าอีเมลมีในระบบไหม) ส่วน 403 ใช้เมื่อรหัสผ่านถูกแต่ยังเข้าไม่ได้: `บัญชีรออนุมัติ`, `คำขอสมัครถูกปฏิเสธ`, `บัญชีถูกระงับ`, `ยังไม่ได้ตั้งรหัสผ่าน` (หน้าบ้านแสดง title/detail ตามที่ส่งมา)
    - ผิดติดกัน 5 ครั้งต่ออีเมล ล็อก 15 นาที (429) และบันทึก Audit Log ทุกครั้งที่เข้าสู่ระบบสำเร็จ
- งานเพิ่ม-ลด (`/projects/{code}/change-orders`, สร้าง/ยืนยันจากลูกค้า/ยกเลิกต้องมี `project.manage`): สร้างแล้วเกิดคำขออนุมัติประเภท `change-order` (ระดับเจ้าของบริษัท) ในศูนย์อนุมัติ ผูกด้วย `approvalId`
    - งานที่ลูกค้าขอ (`source = customer`) อนุมัติไม่ได้จนกว่าจะบันทึกว่าลูกค้ายืนยันแล้ว (409)
    - อนุมัติแล้วหลังบ้านปรับให้: `changeOrderTotal`/`revisedValue` ของโครงการ, เลื่อน `deliveryDate` ตาม `scheduleImpactDays`, เพิ่ม `newTask` เข้าไทม์ไลน์ (รหัส `<ขั้นตอน>.CO<ลำดับ>` ท้ายขั้นตอนก่อนหมุดหมาย) และเพิ่มงวดเงินของงานเพิ่ม-ลด (`changeOrderId`) ต่อท้ายงวดตามสัญญา (งานเพิ่มครบกำหนด 7 วันหลังอนุมัติ งานลดหักจากงวดสุดท้าย)
    - ยกเลิกได้เฉพาะรายการที่รออนุมัติ คำขออนุมัติที่ผูกไว้ถูกปิดด้วย
